# Fetch PRM and gas readings from NERSC

The `dev/purity-overlay` branch contains the complete SSH fetch workflow. No
OneDrive scripts, Windows paths, historical local work directory, or permanent
repository checkout on DAQ05 are required. This guide describes **running the
client on NERSC**, while database queries execute on an authorized reachable host
such as DAQ05. It does not assert that a particular NERSC account already has
network access or credentials.

## What runs where

```text
NERSC: fetch_purity.py from this repository
  -> SSH through the configured gateway
DAQ05: temporary copy of purity_sources.py + lifetime_io.py
  -> read-only PostgreSQL queries using credentials already on DAQ05
  -> raw observations with corrected UTC timestamps returned over SSH
NERSC: validate and rename to snapshot_root/slowcontrols-*.json
  -> watcher -> lifetime.sh -> pooled fits and the monitoring plot
```

This is SSH remote execution, not a PostgreSQL `ssh -L` port-forwarding tunnel.
The helper does not install packages, change DAQ services, schedule itself, or
run detector fits on its caller. Temporary remote code/config/output are removed
when the export finishes. The received snapshot records hashes of the exact two
exporter modules used, so the receiving checkout determines the implementation.

## One-time prerequisites

On NERSC, use a current checkout of the development branch. For the fetch alone,
Python 3.10+ and the `ssh` executable suffice; scientific packages are needed only
by the separate watcher worker/analysis environment.

For a new checkout:

```bash
git clone --branch dev/purity-overlay --single-branch \
  https://github.com/joshuabarrow221/arcube_nearline.git
cd arcube_nearline
```

On the database host, have the operator provision a Python 3.10+ interpreter with
[requirements-export.txt](../actions/lifetime/requirements-export.txt). Those
requirements are NumPy, pandas, SQLAlchemy, psycopg2 and timezone data; no detector
reconstruction or plotting packages are needed. For example, in an approved
user environment on that host, install the requirements file supplied from this
checkout with `python -m pip install -r requirements-export.txt`. The fetch helper
will not install them for you. Select that interpreter using `--remote-python`.

The approved route used during local validation was:

```bash
ssh -J acdcs@acd-gw06.fnal.gov acdcs@acd-daq05.fnal.gov
```

Each student needs authorized access to both hosts. Shared account names in this
example do not grant access. Verify host fingerprints through the normal site
procedure and configure approved authentication. Automated fetches use
`BatchMode=yes` and `StrictHostKeyChecking=yes` for the destination. OpenSSH's
destination options do not generally apply to a `ProxyJump` gateway. After
verifying access and host keys, configure **both hosts** in the receiver's
`~/.ssh/config` (include any aliases used instead of these hostnames):

```sshconfig
Host acd-gw06.fnal.gov acd-daq05.fnal.gov
    BatchMode yes
    StrictHostKeyChecking yes
    ConnectTimeout 15
```

With both hosts configured, unattended fetches fail instead of prompting for
passwords/MFA or accepting unknown host keys. Arrange approved automation access
rather than weakening these settings.

Database credentials stay on the export host. The DAQ05 refresh used its existing
`/home/acd/acdcs/2x2/SlowControls2x2/Cryogenics/config.ini`, section `secrets`, with
keys `host`, `port`, `database`, `user`, `password`. An operator must confirm this
file remains current/readable by the authorized account. It is not in GitHub,
and is neither downloaded nor embedded in snapshots.

## Fetch from a NERSC checkout

Run from the repository root, using actual site paths for the two placeholders:

```bash
# Point at the same flat directory configured as the monitor's snapshot_root.
export ARCUBE_LIFETIME_SNAPSHOT_ROOT=/actual/nersc/purity/snapshots
start=$(date -u -d '48 hours ago' +%Y-%m-%dT%H:%M:%SZ)
end=$(date -u +%Y-%m-%dT%H:%M:%SZ)

python3 extra/data_mgmt/fetch_purity.py \
  --host acdcs@acd-daq05.fnal.gov \
  --jump-host acdcs@acd-gw06.fnal.gov \
  --remote-python /actual/daq05/export-environment/bin/python \
  --source-config actions/lifetime/sources.example.json \
  --credential-ini /home/acd/acdcs/2x2/SlowControls2x2/Cryogenics/config.ini \
  --start "$start" --end "$end" \
  --snapshot-directory "$ARCUBE_LIFETIME_SNAPSHOT_ROOT"
```

`--remote-python python3` is sufficient only if that remote interpreter already
has the required packages. The `--source-config` file is **local to NERSC**;
`--credential-ini` and `--remote-python` refer to **the remote export host**.
The command returns the published JSON path. Inspect its `sources` counts and
measurement timestamps to assess freshness; a new export time does not imply
new PRM measurements. No lifetime plot is generated by this command itself.

The example retrieves PRM, both oxygen channels, water and nitrogen. Nitrogen is
archived with `use_for_lifetime: false`. To query PRM alone, make a local source
config containing only the first source object. Preserve its unit `s` and
`naive_timezone: America/Chicago`; do not convert the units or shift time twice.

The single `--credential-ini` override applies to every PostgreSQL source in the
file, matching the shared PRM/cryogenics database used in our validation. If
sources use different databases, omit this override and set `credential_ini`
and optional `credential_section` separately on each source. Alternatively keep
`url_env`, provided that environment variable is available **to the remote SSH
Python process**. Exporting `PURITY_PSQL_URL` in a NERSC shell does not transmit
it to DAQ05. Do not put credential values in the source JSON or CLI arguments.

## Scheduling and watcher integration

Schedule the fetch on a host allowed to make the SSH connection, using the site's
approved mechanism and frequency. A rolling 48-hour interval allows late rows
and analyzer plateau lookback; retain earlier snapshots. Repeated observations
are deduplicated downstream, and conflicting values fail rather than overwrite.
Neither this helper nor `watcher.py` installs a schedule.

With the monitor configured as described in the [operator guide](lifetime-integration.md),
the existing watcher discovers the new snapshot and queues the lifetime action.
For a manual refresh in the analysis/worker environment, run:

```bash
bash actions/lifetime.sh --monitor-config "$ARCUBE_NEARLINE_LIFETIME_CONFIG"
```

The older `export_purity.sh` plus `sync_purity.sh` path remains supported when the
database host already produces an archive. Choose either SSH fetch or that
producer/rsync route for routine delivery; both yield the same snapshot schema.
The new fetch route does not require a separate rsync step. Its client is light
enough for a transfer host; plotting stays with the configured worker.

## Failure behavior and validation limits

- Queries reuse `purity_sources.export_snapshot`: read-only transactions,
  parameterized windows/tags, 60-second SQL statement timeouts, source-clock
  correction, and an all-enabled-sources success requirement. A gas-query failure
  prevents that attempt from publishing a fresh PRM snapshot as well.
- The client allows 600 seconds for the complete SSH/export by default. Set
  `--timeout-seconds` explicitly for a larger backfill; do not interpret timeout
  as zero measurements. The query interval is inclusive start/exclusive end.
  The client timeout bounds waiting, not guaranteed immediate remote process
  termination; the separate SQL timeout bounds each running database statement.
- SSH failure, malformed/truncated JSON, wrong source/unit/window, or an invalid
  code receipt publishes nothing. A hidden local temporary file is removed;
  existing completed snapshots remain. Successful zero-row queries are valid.
- PRM naive timestamps follow the operator-specified Chicago clock convention.
  Ambiguous/nonexistent daylight-saving times are rejected by the shared adapter;
  resolving such records requires producer-side information. Ignition epoch
  timestamps receive no PRM-style shift.
- Remote exceptions report their type without a potentially credential-bearing
  traceback. Investigate dependencies, credentials, SQL/schema access or clock
  ambiguity in a protected terminal on the export host.

Offline tests exercise the SSH transport boundary and actual shipped exporter
with a simulated database. They do not establish live NERSC routing, current
credentials, host package availability, or a running schedule. These remain
site acceptance checks. The October 19 live refresh predates this launcher and
